I am working on an image steganography project, and at one point, to get a better understanding of the binary code involved, I had Claude write some exercises emanating from the project code. It was so much fun to figure out that I decided to make them into challenges for attendees to solve at my next meetup. I wanted a slide deck that would also serve as a live coding platform where the members could both read what the challenges were and solve them live within the same deck. That way, they wouldn't have to go elsewhere on the web, for example, to write code that outputs results. They could do it right from the slide deck. That's where Slidev came in, and that's why this post. I will walk through how I made Slidev into a Python code runner, a feature which it does not support out of the box (it already runs JavaScript and TypeScript).

## Why Slidev?

Slidev is known as "Presentation slides for developers." It is Markdown-based, which is great, and it provides all sorts of features that focus on presentation interactivity, visual eloquence, and appeal. All those reasons aside, I also like the fact that I could create a Python code runner so that my meetup attendees would have the option of running code directly within the slide deck. That way, they would be able to read *and* write their challenges all in one place!

To install Slidev, run:

```shell
npm init slidev@latest
```

The Slidev installation comes with the default theme.

I had the option of deploying to either Netlify or Vercel: Slidev comes with both a `netlify.toml` and `vercel.json`. But I opted for deploying to GitHub Pages using GitHub Actions and am hosting the slide deck on GitHub.

### Adding tables to a Slidev slide

Adding tables to Slidev slides is easy. It's just a matter of adding a Markdown table. However, if I want to wrap the table in a div, I have to make sure there is a blank line between the opening HTML tag and the beginning of the table and a blank line between the closing HTML tag and the end of the table:

```html
<div class="mt-23 [&_table]:w-[53.5rem]">

| Tool | Use it for | Account needed? |
| --- | --- | --- |
| Slidev (this deck) | Point of reference | No |
| Google Colab | For running the binary challenges in Python | A Google account is required |
| CodeFile | For displaying answers | No |

</div>
```

#### The Slidev UnoCSS utility class

`[&_table]:w-[53.5rem]` is a UnoCSS utility class. UnoCSS, Slidev's CSS engine, is compatible with Tailwind CSS syntax, and the utility class turns into real CSS when Slidev builds the deck.

`[&_table]` is an arbitrary variant. It's a custom selector written inside square brackets. `&` stands for the element the class is on, and `_` stands for a space, which in CSS selectors means "descendant", e.g., `div table`. So `&_table` means "any `<table>` inside this element": in this case, a `div` element.

`w-[53.5rem]` is an arbitrary value. It consists of the normal `w-` width utility, but with a custom value in brackets instead of one of the preset sizes.

Together, on the div that wraps it, `[&_table]:w-[53.5rem]` generates CSS something like:

```css
div table {
  width: 53.5rem;
}
```

Slidev renders the Markdown table as its own `<table>` element inside the `<div>`, so I can't put a regular CSS class directly on the table. The arbitrary variant reaches into the div and styles the table from outside.

I replaced a `<style>` block with a UnoCSS utility class. I still could have used a global stylesheet, e.g., `style.css` at the root of the repo, or `styles/index.css`. But why didn't I? Because the global styling would have styled *all* tables in the slide deck instead of a specific table within a specific slide.

#### The reason why I didn't use a style block to style my Markdown table

But the real question is, why didn't I just use the style element to style the table? Because Vue, which Slidev is built with, turns a `<style>` block into a separate virtual CSS import. Slidev 53's new import guard, a security check, sees that import as coming from outside the allowed files and blocks it.

So when I initially used the `<style>` code block in slide 3, it threw an error in the Terminal console:

```text
[vite] Internal server error: [slidev] Import "/slides.md__slidev_3.md?vue&type=style&index=0&scoped=9a47da91&lang.css" from slide Markdown resolves outside of Vite server.fs.allow: /slides.md__slidev_3.md
  Plugin: slidev:slide-import-guard
```

I resolved the issue by adding a UnoCSS custom utility class and value on the div wrapping around my Markdown table.

## Creating the Related resource slide

Creating the layout for the Related resource slide was not difficult to achieve. It was creating the QR code that was new for me.

First, I installed the Homebrew package called `qrencode`:

```shell
brew install qrencode
```

Then, from the deck repo root I ran:

```shell
qrencode -t SVG -m 2 -o public/qr-tutorial.svg "https://thepythoncode.com/article/hide-secret-data-in-images-using-steganography-python"
```

- `-t SVG` creates an SVG, which renders a sharp image quality at any size in the browser window (use `-t PNG -s 10` for a PNG instead).

- `-m 2` sets a small quiet zone[^1] around the code.

- `-o public/` puts the QR code SVG in `public/`, where Slidev serves it as is.

The default color scheme is black on white. This contrast produces the most reliable scans, especially on a dark slide.

On the slide, I referenced it with a forward slash:

```html
<img src="/qr-tutorial.svg" class="w-40" />
```

However, since I was going to host the slide deck on GitHub Pages, later I ran `npm run build -- --base /debug-table-binary-exercises/`. `--base` is an option I passed to the build that rewrote the QR code path automatically. The built `src` became `/debug-table-binary-exercises/qr-tutorial.svg`.

## Creating the Pyodide code runner

### Running Python on the slides: introducing Slidev's code runner feature

I mentioned earlier on that part of the reason I chose Slidev to build the slide deck for my meetup event was its code runner feature. Slidev, and Slidev's code runner feature, don't include running Python code directly in a slide. Out of the box, Slidev, with the help of its Monaco editor, runs JavaScript and TypeScript code in slides.

To run Python code in slides is more complex. To get Python to run in my Slidev presentation, I added it with a custom runner in `setup/code-runners.ts`:

```ts
// setup/code-runners.ts
import { defineCodeRunnersSetup } from '@slidev/types'

const PYODIDE_URL = 'https://cdn.jsdelivr.net/pyodide/v0.28.0/full/pyodide.mjs'

let pyodidePromise: Promise<any> | undefined

function getPyodide() {
    pyodidePromise ??= import(/* @vite-ignore */ PYODIDE_URL)
        .then(module => module.loadPyodide())
    return pyodidePromise
}

export default defineCodeRunnersSetup(() => {
    return {
        async python(code) {
            const pyodide = await getPyodide()
            const lines: string[] = []
            pyodide.setStdout({ batched: (line: string) => lines.push(line) })

            const output = () => lines.map(line => ({ text: line }))

            try {
                await pyodide.runPythonAsync(code)
            } catch (err: any) {
                const errorLines = String(err.message ?? err).split('\n')
                const start = errorLines.findIndex(line => line.includes('File "<exec>"'))
                const useful = start === -1 ? errorLines : errorLines.slice(start)
                return [
                    ...output(),
                    ...useful.filter(line => line.trim()).map(line => ({ error: line.replace(/ /g, '\u00a0') })),
                ]
            }

            return output()
        },
    }
})
```

There are two parts to the code.

The first part is Slidev's code runner hook: `defineCodeRunnersSetup` is a helper function that enforces a contract. A contract is a programming term for an agreement (aka interface) between two pieces of code about how to work together. It consists of what one side provides and what the other side promises to do with it. Neither side needs to know how the other side works. They only need to stick to the agreement.

For the code runner, the agreement (aka interface) is:

My code promises an object whose keys are language names, and whose values are functions that take the code as a string and return output objects `({ text }, { error }, or { html })`.

Slidev promises to call my function when ▶ is pressed, pass it the editor's code, and display whatever I return.

The second part is an interpreter in the browser (my code loads it). JavaScript runs in the browser out of the box because browsers run JavaScript natively. Python is not native to the browser, so the code runner has to include it.

That's where Pyodide comes in:

> *Pyodide is a port of CPython[^2] to WebAssembly/Emscripten.* — *[What is Pyodide?](https://pyodide.org/en/stable/)*

> *Emscripten is a complete compiler toolchain to WebAssembly, using LLVM, with a special focus on speed, size, and the Web platform.* — *[emscripten.org](https://emscripten.org)*

Pyodide makes Python runnable in the browser, and micropip installs Python packages into it. According to the Pyodide documentation:

> *Any pure Python package with a wheel available on PyPi is supported.* — *[What is Pyodide?](https://pyodide.org/en/stable/#:~:text=Any%20pure%20Python%20package%20with%20a%20wheel%20available%20on%20PyPi%20is%20supported.)*

### Four main points to know regarding the Slidev Python code runner

1. Slidev's hook consists of a language key plus a function that receives the code and returns output.
1. Python needs help because browsers only run JavaScript, so Pyodide delivers real Python as WebAssembly.
1. Load Pyodide once, and reuse: the first run downloads Pyodide, which is why I warm it up on slide 5.
1. Capture and clean up output by redirecting `print()`, and then trim errors down to the useful part so the error shown on the slide points at the learner's code.

## Creating GitHub Pages Actions

First, I had to go to my remote repo inside Settings → Pages → Build and Deployment → Source and choose GitHub Actions. This tells GitHub to publish whatever my workflow builds instead of publishing a branch like gh-pages, for instance.

Next, the Slidev documentation had an example `.github/workflows/deploy.yml` that I could work with if I wanted. To view it, please visit the [Building and Hosting](https://sli.dev/guide/hosting#github-pages) documentation on Slidev. But I created my own file locally at the root of the local repo:

```shell
mkdir -p .github/workflows
```

Then I had to create a `deploy.yml` file inside workflows:

```shell
touch .github/workflows/deploy.yml
```

Then I added the `deploy.yml` contents. Below is my original version, with older actions:

```yaml
name: Deploy pages

on:
  workflow_dispatch:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v5

      - uses: actions/setup-node@v5
        with:
          node-version: 'lts/*'

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build -- --base /debug-table-binary-exercises/

      - name: Setup Pages
        uses: actions/configure-pages@v5

      - uses: actions/upload-pages-artifact@v4
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

I share the updated `deploy.yml` version a bit later in the post.

Going back to `npm run build -- --base /debug-table-binary-exercises/`, this command makes sure that my deck won't reside at the root of a domain. It will be at `https://interglobalmedia.github.io/debug-table-binary-exercises/`.

Without `--base`, Slidev builds the site as if it lives at the root, so the page asks for files like `/assets/index.js`, which the browser looks for at `https://<username>.github.io/assets/index.js`. Nothing is there, so the deck loads blank. `--base` tells Slidev to put `/debug-table-binary-exercises/` in front of every path, so the files are found.

### Breaking down the deploy.yml code

The first section involves when the GitHub Actions workflow runs and what it is allowed to do:

```yaml
name: Deploy pages

on:
  workflow_dispatch:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: false
```

- **`on`:** The workflow runs on every push to the remote `main` branch. `workflow_dispatch` also gives me a "Run workflow" button on the Actions tab, so I can rerun it without having to push to remote again.
- **`permissions`:** This allows the workflow to read the repo and write to Pages.
- **`id-token`:** The `write` permission lets the deploy step prove to Pages that it's this repo's workflow.
- **`concurrency`:** If I push twice quickly, the second deploy waits for the first to complete instead of both running at once.

The second part consists of the build job. It's where `npm ci`, the build, and `--base` come in:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v7

      - uses: actions/setup-node@v7
        with:
          node-version: 'lts/*'

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build -- --base /debug-table-binary-exercises/

      - name: Setup Pages
        uses: actions/configure-pages@v6

      - uses: actions/upload-pages-artifact@v5
        with:
          path: dist
```

- **`checkout`:** copies my repo onto GitHub's machine.
- **`setup-node`:** installs Node. `lts/*` means the current long-term-support version.
- **`npm ci`:** provides a clean install from `package-lock.json`, exactly the package versions I have locally. It is stricter than `npm install`, which suits builds.
- **`build`:** runs my `build` script (`slidev build`). The `--` passes `--base ...` through to Slidev instead of npm. `--base` matters because the site lives at `username.github.io/debug-table-binary-exercises/`, not at the root.
- **`configure-pages`:** prepares the Pages setup for the run. It reads the repo’s Pages settings and makes details like the site’s URL available to later steps.
- **`upload-pages-artifact`:** packages and uploads static files via the `dist/` folder that can be deployed to GitHub Pages.

The third section consists of the deploy job:

```yaml
deploy:
  needs: build
  runs-on: ubuntu-latest
  environment:
    name: github-pages
    url: ${{ steps.deployment.outputs.page_url }}

  steps:
    - name: Deploy to GitHub Pages
      id: deployment
      uses: actions/deploy-pages@v5
```

An environment in GitHub Actions is a named deployment target. `github-pages` is the one GitHub creates for Pages when I set Settings → Pages → Source to GitHub Actions:

![Screenshot of setting debug-table-binary-exercises Source to GitHub Actions](Screenshot-2026-10-12-at-10.37.59-AM.webp)

*Screenshot of setting `debug-table-binary-exercises` Source to GitHub Actions*

Naming the environment accomplishes the following:

- It records the deployment. Each run appears under "Deployments" on my repo page, with a history of when the site was deployed.
- It applies the environment's rules. Environments can have protection rules (which branches are allowed to deploy, for example).
- `url` is the link GitHub shows for that deployment. It appears in the deploy job's box, on the run summary page, and in the Deployments list:
  - `${{ ... }}` is GitHub's expression syntax. It means "work out what is between the curly braces when the workflow runs."
  - `steps` means the steps of the particular job.
  - `deployment` is the step's `id`. That's what connects the environment URL with the deploy step.
  - The `deploy-pages` action deploys the site and then outputs my live site's address represented by `outputs.page_url`: `https://interglobalmedia.github.io/debug-table-binary-exercises/` in the case of the debug-table-binary-exercises slide deck. GitHub fills in the environment URL once the job has completed.

In the `steps` section of the deploy job:

- The step's `name` is the label I see in the run's log as in the screenshot below: `Deploy to GitHub Pages`.
- The step's `id: deployment` gives the step a name other parts of the job can refer to.

Why did this happen? Vite 8 switched its CSS minifier from esbuild to lightningcss. The reported issue on the vitejs/vite GitHub repository was [related to mine](https://github.com/vitejs/vite/issues/22649). The lightningcss minifier crashed while minifying the same CSS that Vite 7 had successfully minified. My fix was to turn off CSS minification. I did this by adding `cssMinify: false` to my `vite.config.ts`. However, Slidev’s starter did not come with a `vite.config.ts` file. I had to create one.

So I created what I thought was `vite.config.ts`, and added the following code to it:

```ts
import { defineConfig } from 'vite'

export default defineConfig({
    build: {
        cssMinify: false,
    },
})
```

Then I ran `npm run build -- --base /debug-table-binary-exercises/` again and got the same error.

I couldn't understand why I still had errors. But at one point I went into my slide deck repo, and realized that I had created a `vite-config.ts` file, *not* a `vite.config.ts` file. I changed the name, and ran the build again:

## The Slidev MCP server

Last, but not least, I want to talk about Slidev's [MCP server](https://sli.dev/features/mcp): partially because I am going to build my own MCP server, and partially because I wanted to share what it does both for my own edification and for others'.

### Code runner vs MCP server

| Category | Code runner | MCP server |
| --- | --- | --- |
| What it is | A function I write in `setup/code-runners.ts` with `defineCodeRunnersSetup`. Slidev calls it. | A program built into Slidev that offers tools to an AI client. I don't write it. |
| What triggers it | Someone pressing ▶ on a code block in the deck. | An AI client such as Claude Code or the Claude desktop app calls one of its tools. |
| Is AI involved? | No. | AI is the caller. |
| Where it runs | In the viewer's browser. Pyodide runs Python as WebAssembly. | On my Mac, two ways. HTTP: inside the dev server at `http://localhost:3030/__mcp`. stdio: as its own process, started by the AI client. |
| What it does | Runs code and returns output lines, which Slidev shows under the block. | Reads, edits, inserts, removes, and moves slides, and navigates to a slide (the eight tools). It doesn't run code. |
| Works on the deployed GitHub Pages deck? | Yes. It's part of the build, and Pyodide loads from the CDN. | No. It exists only while `npm run dev` (or `npx slidev mcp slides.md`) is running. The static build has no server. |
| How I turn it on or off | It exists because I wrote it. Remove the `python` function and Python blocks can't run. | HTTP: on by default, turned off with `mcp: false` in the headmatter. stdio: runs only when it's started. |
| What defines how it talks | Slidev's own contract. The function receives the code and returns `{ text }` or `{ error }` objects. | The Model Context Protocol, an open standard any MCP client can use. |

When I run `npm run dev`, Slidev starts two things side by side: the deck in my browser, and an MCP server at `http://localhost:3030/__mcp`:

The server provides an AI client eight tools for working on my slide deck:

- The AI client can read the deck: 
  - `slidev-get-info` (an overview)
  - `slidev-list-slides` (number, title, and layout of every slide)
  - `slidev-get-slide` (one slide's frontmatter, content, and notes)
- The AI client can change the deck: 
  - `slidev-update-slide`
  - `slidev-insert-slide`
  - `slidev-remove-slide` 
  - `slidev-move-slide`
- The AI client can drive the live presentation: 
  - `slidev-goto-slide` (only while the dev server is running)

### What the MCP server could do for me

I'd connect an AI client (e.g. Claude Code, with `claude mcp add --transport http slidev http://localhost:3030/__mcp`) and ask in plain language via text prompts:

- "List my slides and their layouts." → `slidev-list-slides`
- "Add speaker notes to slide 5 reminding me to run it during setup." → `slidev-update-slide`
- "Insert a slide after slide 9 with the top-title-two-cols layout." → `slidev-insert-slide`
- "Go to slide 10." → `slidev-goto-slide`, and the browser jumps there

The AI then changes `slides.md` via those tools. Each change lands in the browser right away through the dev server's live reload.

## Conclusion

In this post, I walk through the process of building a slide deck for my Debug Table meetup's second gathering with the web-based slides maker called Slidev. I discuss the problems I had building the deck because of Vite 8's switch from esbuild to lightningcss for minifying CSS and the workaround I implemented. 

I talk about the various features Slidev has to offer and which ones I employ. One important feature I use, which was integral to the meetup event, is adding a Python code runner so attendees could write live Python code directly in a slide and get back their code's output with the press of a play button. 

Working through creating the binary challenges freed me from being stuck on a piece of code I have been working on in my image steganography project. The challenges emanate from working on binary exercises to better understand what was going on with the encoding and decoding of messages in my image steganography project. I was especially struggling with how to modify the code in my `decode_message()` function to reflect the change I was going to make to the message decoding process. Revisiting the challenges and organizing the answers for the meetup resulted in an "aha" moment. Specifically, how `decode_message()` should return the raw bytes. Originally, `decode_message()` treated two-byte UTF-8 characters as two separate characters. By modifying the code to join the two bytes, `decode_message()` will return the two-byte character as one, such as é, correctly, instead of garbage.

Lastly, even though I haven't used the Slidev MCP server feature yet with this deck, I have included it because I will be using the Slidev MCP server to interact with this slide deck. So I wanted to share a taste of what it has to offer. I will also be building my own MCP server, so learning about Slidev's server gave me a better understanding of how MCP servers work under the hood.
